# DeepSeek Harness コンテキストウィンドウ選択プラグイン

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md) | [한국어](README.ko.md)

![License](https://img.shields.io/badge/license-MIT-blue.svg)
![Platform](https://img.shields.io/badge/platform-DeepSeek%20Harness%20%3E%3D%200.2.1--rc.2-informational)

DeepSeek Harness 用のバンドルで、**Qoder** と **Trae** のリバースプロキシ経由で提供されるモデルに対して、入力欄の隣にコンテキストウィンドウの選択 UI を追加します。

選択した値は、Harness が公開している設定 API を通じて、そのモデルのプロバイダーカタログ上の `contextWindow` に書き込まれます。したがって、これはラベルやキャッシュされた注記ではなく、リクエストの見積もり、コンテキスト使用量メーター、圧縮の発動判定に実際に使われる値です。

---

## 概要

Harness は会話のトークン予算を、選択中モデルのアダプターメタデータのみから決定します。セッション単位の上書きは存在しないため、サポートされた調整点はプロバイダーカタログの項目そのものだけです。

本バンドルは、その調整点をワンクリックの操作として提供します。対象は実際にウィンドウを変更できるゲートウェイに限定し、メニューには各モデルが公表しているウィンドウのみを表示します。

## 動作原理

`conversation.input.right` スロットに 1 つの項目を登録し、選択時に `settings/mutate` を 1 回だけ実行します。

```text
llm-pi-ai → providers.<provider>.models[<index>].contextWindow = <tokens>
```

これは「設定 → モデル」ページが行う書き込みと同一であり、追加の権限も副作用も伴いません。その後 Harness はこのカタログ項目から次を導出します。

- リクエストごとに記録される `request/context.contextWindow`
- コンテキスト使用量メーターの分母
- `dsh-compaction-basic` の圧縮しきい値

モンキーパッチ、DOM 注入、`localStorage` の使用、認証情報の読み取りはいずれも行いません。

## 対応ゲートウェイ

上流が実際にウィンドウ変更を受け付けるゲートウェイのみを対象とします。**WorkBuddy は意図的に対象外**です。同サービスは選択可能なウィンドウを受け付けないため、そこに操作を置くことは提供できない機能を約束することになります。

ゲートウェイの判定は、まずプロバイダー ID（`qoder-intl-proxy`、`qoder-cn-proxy`、`trae-proxy`）で行い、次に該当ポート（8790、8000）のループバック `baseURL` で行います。したがって、名前を変更したプロバイダーでも一致し、リモートのプロバイダーは決して一致しません。

### Qoder

Qoder はモデルごとに利用可能なウィンドウを公表しています。メニューにはその値のみを表示し、単一のウィンドウしか持たないモデルは固定チップとして表示します。

|---|---|---|
| `Auto` | 200K（固定） | 200K（固定） |
| `Qwen3.8-Max`、`Qwen3.8-Flash`、`Qwen3.7-Max`、`Qwen3.7-Plus`、`Qwen3.7-Flash` | 200K / 400K / 1M | 200K / 400K / 1M |
| `DeepSeek-V4-Pro`、`DeepSeek-Flash` | 200K / 400K / 1M | 200K / 400K / 1M |
| `GLM-5.3`、`GLM-5.3-Flash`、`GLM-5.2` | 200K / 400K / 1M | 200K / 400K / 1M |
| `Kimi-K3`、`Kimi-K2.8-Preview` | 200K / 400K / 1M | 200K / 400K / 1M |
| MiniMax | 200K（固定） | 200K / 400K / 1M |
| `Ultimate`、`Sonus`、`Cantus` | — | 200K / 400K / 1M |
| `Performance` | — | 272K / 400K / 1M |
| `Efficient` | — | 200K（固定） |

### Trae

Trae はモデルごとに 2 つのウィンドウのみを持ちます。リレーのアカウントカタログ（`context_window_tokens.dev` と `.max`）から取得した、標準ウィンドウと任意の 1M プロファイルです。

| モデル | 標準 | 1M プロファイル |
|---|---|---|
| `deepseek-v4.1-flash`、`DeepSeek-V4-Flash-Official`、`DeepSeek-V4-Pro-Official`、`glm-5.2`、`glm-5.3`、`glm-5.3-flash`、`glm-5.3-flashx`、`kimi-k3`、`minimax-m3`、`minimax-m3.1-flash`、`qwen3.8-max`、`qwen-3.7-plus`、`step-5-preview` | 200K | 1M |
| `mimo-v2.6-flash`、`mimo-v2.6-pro` | 200K | 981,504 |
| `Doubao-Seed-2.1-Pro`、`Doubao-Seed-Evolving` | 256K | 1M |
| `Doubao-Seed-2.1-Turbo`、`Doubao-Seed-Code` | 256K | —（固定） |
| `kimi-k2.6`、`kimi-k2.7-code` | 200K | —（固定） |

1M プロファイルは本バンドルではなくリレー側の機能です。リレー自身の Max モードが無効な場合、1M でのリクエストはフォールバックするか失敗します。その場合は標準ウィンドウを選択してください。

## ゲートウェイ実装

本バンドルはカタログの値を変更するだけで、上流の実装やプロキシは行いません。対象となる 2 つのゲートウェイは独立したプロジェクトです。

| ゲートウェイ | 実装 |
|---|---|
| Qoder | [`shuishuipingan/qoder2api-hub`](https://github.com/shuishuipingan/qoder2api-hub) |
| Trae | [`autumnsentiment/Trae2api-cn`](https://github.com/autumnsentiment/Trae2api-cn) |

いずれかを先に導入し、`llm-pi-ai` のプロバイダーとして接続してから、本バンドルは意味を持ちます。上記のモデル別ウィンドウは各ゲートウェイが公表している値（Qoder のモデルカタログ、Trae リレーのアカウント `context_window_tokens`）に基づくため、ゲートウェイ側でウィンドウが変更された場合は、この表を更新する必要があります。

## インストール

本バンドルは通常の Harness プラグインパッケージです。`package.json` が `dsh.bundle.patch` と `dsh.client` を宣言し、`cordis.patch.yml` がプラグイン行を挿入します。

```text
plugin_manager.install_bundle  github:THao712/dsh-ctx-window
```

ローカルのチェックアウトも同様に、GitHub 指定の代わりにそのディレクトリを渡してインストールします。

要件：

- DeepSeek Harness 0.2.1-rc.2 以降
- 対応ゲートウェイを 1 つ以上含む `llm-pi-ai` プロバイダー設定
- 初回インストール後のページ再読み込み（クライアントモジュールは起動時に読み込まれます）

## 使い方

1. 対応ゲートウェイのモデルを選択します。
2. 送信ボタン横の **コンテキスト** コントロールを開きます。
3. ウィンドウを選択します。メニューにはカタログの元の値、直前のリクエストで使われたウィンドウ、および選択値が元の値を超える場合の警告が表示されます。

各モデルには **自動（モデルの既定値）** も用意されており、本バンドルが書き込む前の値を復元します。また、検証済みの任意の整数（`1 … 4,000,000`）も指定でき、ゲートウェイが受け付けるものの公表していないウィンドウに対応します。

選択値は**次回**のリクエストから有効になり、現在のリクエストは準備時のウィンドウを維持します。メニューは両方を表示するため、まだ反映されていない書き込みは推測ではなく明示されます。

## 検証

実環境で確認済みです。

- `qoder-cn-proxy` → `DeepSeek-Flash` での選択により、プロファイルカタログに `contextWindow: 400000` が書き込まれ、同プロバイダーの他のモデルは変更されませんでした。
- 直後のリクエストは `request/context` に `{provider: "qoder-cn-proxy", model: "DeepSeek-Flash", contextWindow: 400000}` を記録し、ゲートウェイは正常に応答しました。
- `trae-proxy` → `deepseek-v4.1-flash` を `1,000,000` に設定した場合、連続する 2 回のリクエストがいずれも `contextWindow: 1000000` を記録し、双方とも応答がありました。

## 設計上の制約

コンテキストウィンドウは**モデル**に属し、セッションには属しません。Harness にはセッション単位の上書きがありません。`LlmCallConfig` にウィンドウのフィールドはなく、アダプターはプロバイダーごとに排他的で、解決処理のインターセプト点も存在しません。そのため本バンドルは、そのモデルを使うすべてのセッションで共有されるカタログ項目を変更します。同一モデルの 2 つのセッションで異なるウィンドウを持たせることはできません。

選択 UI はメニューを各モデルの公表値に制限しますが、任意のカスタム値を上流が受け入れるかどうかは検証しません。サービスの実際の容量を超えるリクエストは、そのサービス側で拒否されます。

## 既知の上流の問題

`trae-proxy` は、ターンの途中のステップで `Object of type set is not JSON serializable`（`PI_AI_ERROR`、使用量カウンタはすべて 0）により断続的に失敗することがあります。この事象は本バンドルが存在する前から観測されており、設定したウィンドウとは無関係にターンの最初のステップでも後続ステップでも発生し、リクエストがアダプターを離れる前に起きます。再試行で回復します。修正すべきはリレー側です。

## アンインストール

バンドルを無効化または削除してください。サービス、リスナー、セッション状態は保持していません。既に書き込まれた値はプロファイルカタログに残るため、**自動** または「設定 → モデル」ページで戻せます。
